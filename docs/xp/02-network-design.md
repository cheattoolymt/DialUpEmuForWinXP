# Step 2: XP上のネットワーク方式の設計判断

状態: **方式を選定。実装・XP実機での成立確認は未実施。**
対象: Windows XP SP3 / x86、同じPC上のRASとエミュレータ。
根拠は [sources.md](sources.md) のIDで示す。

## 守る仕様

- エミュレータ起動中は、他アプリのLAN/Wi-Fi直接利用を制限する。
- ダイアル前・RAS切断後は通常アプリからインターネットへ出ない。
- 接続中はRAS→仮想COM→PPPを通った通信だけを実インターネットへ出す。
- 解除・終了でLAN/Wi-Fiの通常利用へ戻す。異常終了で制限を残さないことも必須。
- NIC自体は無効化しない。ARP/DHCP等の必要な回線維持通信は限定して許可する。
- IPv6がインストールされていても物理NIC経由の抜け道を残さない。PPPは当面IPv4のみ。
- 既存の別製品の制限・ドライバ設定を勝手に上書きしない。

これは通常のアプリ通信を制限する機能。管理者がドライバを停止・改変する操作まで
防ぐセキュリティ境界とはしない。未知のNICや既存VPNの扱いを推測で許可しない。

## 候補の比較

| 候補 | 評価 | 判断 |
|---|---|---|
| WFP＋`IP_UNICAST_IF`をそのまま使う | XPでは利用できない (S01/S02) | 不採用 |
| 送信元IPだけbindする／メトリック変更・宛先別routeを足す | 前者は送信IFの固定を保証しない。後者は他アプリにも影響するため、専用化と自己参照回避を単独で満たさない | 不採用 |
| プロキシ設定だけを変更する | 設定を使わないアプリやUDPを制限できない | 不採用 |
| LSP/TDIでプロセスを識別する | XPの仕組みとして存在する (S01)。別途、経路固定と広いプロトコルの制御が必要 | 予備案。今回の第一候補にしない |
| NDISでホストの通常通信を止め、PPPのIPをNATしてNICへ直接送る | 通常のWinsockの外向き経路を使わずに済む。NATと障害復元の追加実装が必要 (S09/S10/S11) | **選定する方式** |
| XPをVM内のRASクライアントにし、本体を別OSへ出す | 作業を減らせるがXP上で本体を動かす構成とは異なる | 今回は対象外 |

## 選定: NDIS 5.x系のパケットI/O＋PPP直結NAT

```mermaid
flowchart LR
  A[XPのアプリ] --> R[RAS / PPP]
  R --> C[仮想COM]
  C --> P[既存のAT / HDLC / PPP]
  P --> N[XP用パケットNAT]
  N --> D[XP対応NDISパケットI/O]
  D --> E[選択したEthernet / Wi-Fi]
  E --> I[インターネット]
  H[ホストTCP/IPの物理NIC直接通信] --> G[全対象NICの送受信制御]
  G --> M[限定したARP / DHCP等のみ通す]
```

逆方向は物理NICで受信→既存NATフローに一致する応答を逆変換→`vm_ppp_send_ip()`→RAS。
**NDIS上で流れているPPPのフレームを取り出す方式ではない。** 既存の仮想COM上の
PPP処理を入口とする。RASインターフェースを物理NICの遮断対象に含めない。

XP版では、当面libslirpをインターネット接続の主バックエンドにしない。
libslirpはホストのTCP/UDPソケットを使うため、そのまま残すとXP上のIF指定問題が残る。
既存libslirp経路は元版の回帰検証用として維持し、XP用の別バックエンドを将来追加する。
**この判断は今後のStep 3の依存DLL選定も変更する**。XP製品側にlibslirp/GLibを
必須とするかは新バックエンドの依存関係を決めてから確定する。

これは技術資料に基づく設計上の選択であり、このPC構成で動くことの実証ではない。
特にS11のサンプルは通常のLAN共有であり、同一PCのRASと直接接続する今回の実証ではない。

## I/Oドライバの候補と採用条件

評価候補は **WinpkFilter v3.6.1アーカイブのXP用legacyドライバ** (S08)。
新しいNDIS6用MSIや最新版の全機能がXPでも使えるとは扱わない。

選定しているのはNDISレベルの方式であり、WinpkFilterの製品・ライセンス採用を
確定したわけではない。旧版で最低限必要なAPI、復元、配布条件が通らなければ採用しない。
その場合はXP対応の専用NDIS 5.x中間ドライバを作る案へ戻し、工数と導入手順を再設計する。
未確認のドライバを自動取得・インストールする処理は今回追加しない。

最低限のI/O契約:

- アダプタ列挙・MAC/IP/MTUの確認、物理NICとRASの区別。
- 対象全NICの双方向TUNNEL相当。LISTENのみでは原本が通るので不可 (S09)。
- 明示したNICハンドルへのEthernet注入 (S10)、受信通知とキュー回収。
- 通常TCP/IPへ渡すフレームの明示的な再注入。
- 設定所有者の識別と復元。既存の他製品のフィルタを共有・破壊しない。
- NIC追加/切断、復帰に対して、排他状態を維持できないならセッションを解除する。
  追加NICの最初の通信を防げることはユーザモード通知だけでは保証しない。
  ドライバ側で可能かを検証し、保証できない場合は対応範囲を明示して再設計する。

## パケット処理の責任

| 処理 | 設計する内容 |
|---|---|
| PPP入力 | IPCPで確立したクライアントIPv4のみ受け付ける。長さ、checksum、断片、上限を検証 |
| 送信先 | 物理側IP/mask/gatewayから同一リンクかgatewayかを決め、ARPでMACを解決。Windowsのグローバルなroute変更はしない |
| NAT | IPv4 TCP/UDPのアドレス・ポート変換、5-tupleごとのフロー表、期限、上限、切断・再接続時の破棄 |
| ポート競合 | ホストの使用中ポートと衝突しないよう、WinSockで物理IPv4のポートを予約する案を検証。予約ソケットでconnect/sendは行わない。予約可否・SO_EXCLUSIVEADDRUSEの挙動は実機ゲート |
| 戻り通信 | 選択NIC・IP・ポート・相手先がフローに一致する応答だけをPPPへ渡し、同じ応答をホストTCP/IPへ重複配送しない |
| TCP | 接続の終端はRAS側OS。新バックエンドはNATのみでTCPを再実装しない。FIN/RST、再送、SYN再試行でマッピングが壊れないことを確認 |
| checksum / TTL | IP/TCP/UDP checksum、TTLと期限切れ処理を仕様化。IPv4 UDPのzero checksumを正しく扱う |
| ICMP / MTU | Echo IDと返送、ICMPエラーに引用された内側IP/portの逆変換、fragmentation-neededを扱う。断片は有界な再構成等を設計し、非先頭断片をポートなしで誤転送しない |
| DNS | IPCPで明示した上流DNSへ通常のUDP/TCP NATで送る。ホストDNSの自動検出や仮想DNS自身への転送を避ける |
| DHCP / ARP | ホストのDHCP更新とARP維持を必要なNIC・形式・相手に限定して通す。一般のUDP許可にはしない。IP/gateway変化時は古いNATを破棄し再確立 |
| Wi-Fi維持 | EAPOLなど接続維持に必要な非IPフレームを実機で確認。形式がEthernet互換という推測だけでWi-Fi対応済みにしない |
| IPv6等 | 通常アプリの物理IPv6は通さない。管理例外以外の未知EtherType等は専用化中の許可対象にしない |

NDISドライバは通常のパケットI/Oを提供するだけで、上記NATや復元方針を自動実装しない。
既存 `vm_eth.c` はlibslirp向け疑似Ethernet/ARP層で、物理側のgateway ARP処理を
そのまま満たすとは扱わない。既存のchecksumヘルパ等は個別に再利用を検討する。

## 状態遷移と解除

1. `NORMAL`: 通常のLAN。NIC設定とドライバ状態を読み取る。
2. `PREPARING`: 所有権と後始末を確保し、必要な全NICを準備する。
3. `EXCLUSIVE_IDLE`: 全対象NICの制御完了後のみ「待機中」と表示。アプリの直接通信は禁止。
4. `PPP_UP`: PPPで届いた通信だけをNATする。
5. RAS切断でフローを破棄して`EXCLUSIVE_IDLE`へ戻る。LAN直接利用はまだ再開しない。
6. 明示解除・本体終了・異常時はPPPを落とし、注入を止めてキュー/フロー/所有設定を解除。
7. `NORMAL`への復元を確認する。

途中のNICで準備が失敗した場合、準備済みのNICだけ制限された状態を残さず巻き戻して
起動を失敗させる。排他できていないのに接続成功や専用化成功と表示しない。

異常終了時の復元には、ハンドルが閉じるだけでなくドライバ側の後始末が必要 (S13/S14)。
旧WinpkFilterの自動復元は未確認。保証できなければ採用を止める。
自作ドライバではfile-object所有セッションを`IRP_MJ_CLEANUP`で解除し、
ハンドルを他プロセスへ継承・複製させない。ハング対策としてドライバ側の期限付きleaseを
検討する。復元目標は本体終了後5秒以内とし、これは設計目標で実測値ではない。
永続filter/startup modeやIP設定の恒久書換えは使わない。
